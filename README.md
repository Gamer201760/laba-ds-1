# Лабораторная работа №2 по курсу «Дискретный анализ»

Исследование скорости и потребления памяти словаря на AVL-дереве из первой лабораторной,
исправление найденных ошибок и недочётов. Полный отчёт — [`report/report.pdf`](report/report.pdf).

## Задача

Словарь: ключ — регистронезависимое слово из английских букв длиной до 256 символов, значение —
число от 0 до 2⁶⁴−1. Команды:

| Команда | Действие | Ответ |
|---|---|---|
| `+ word 34` | добавить слово | `OK` / `Exist` |
| `- word` | удалить слово | `OK` / `NoSuchWord` |
| `word` | найти слово | `OK: 34` / `NoSuchWord` |
| `! Save path` | сохранить словарь в бинарный файл | `OK` / `ERROR: ...` |
| `! Load path` | загрузить словарь из файла | `OK` / `ERROR: ...` |

Нужно исследовать программу через `gprof` и `dmalloc` (можно добавлять другие средства), найти и
исправить недочёты, сравнить с предыдущей версией.

## Структура

```
old/B.cpp        версия из первой лабораторной
new/B.cpp        исправленная версия
tests/gen.py     генератор тестов
tests/bench.py   замер времени и памяти (лучшее из 5 запусков)
logs/            выводы gprof, valgrind, dmalloc, gcov
report/          отчёт в LaTeX по шаблону MAI-da/report_pattern
```

## Сборка и запуск

```bash
g++ -O2 -o b new/B.cpp
./b < input.txt

# тесты
uvx python tests/gen.py 1000000 mix > tests/mix_1000000.txt      # режимы: mix, insert, sorted, saveload
uvx python tests/bench.py ./old_b ./new_b tests/*.txt

# профилирование
g++ -O2 -pg -o bpg new/B.cpp && ./bpg < tests/mix_1000000.txt > /dev/null && gprof -b -p bpg gmon.out
valgrind --tool=callgrind ./b < tests/mix_100000.txt > /dev/null
valgrind --tool=massif ./b < tests/saveload_200000.txt > /dev/null && ms_print massif.out.*

# dmalloc
g++ -O2 -g -DDMALLOC -DDMALLOC_FUNC_CHECK -o bdm new/B.cpp -ldmalloccxx
eval `dmalloc -b -l dm.log -i 100 high`
./bdm < tests/mix_100000.txt > /dev/null

# отчёт
cd report && docker run --rm -v $PWD:/w -w /w texlive/texlive pdflatex report.tex
```

## Используемые средства

- `gprof` — плоский профиль по функциям программы;
- `dmalloc` 5.5.2 — проверка кучи, заборы вокруг блоков, неосвобождённые указатели;
- `valgrind` 3.19 — `memcheck` (утечки), `callgrind` (инструкции, включая `libstdc++`), `massif` (график кучи);
- `gcov` — покрытие кода тестами;
- `/usr/bin/time`, `ulimit -v`, `ulimit -f` — пиковая память и искусственные системные ошибки.

## Найденные недочёты

Ошибки:

1. Ввод не проверялся: `+ abc` без номера добавлял слово с мусорным значением, слова с цифрами и
   длиннее 256 символов принимались.
2. Из-за этого `Save` создавал файл, который `Load` сам не мог загрузить.
3. `! Foo path` и `! Load` без пути считались загрузкой несуществующего файла и молча очищали словарь.
4. Номер больше 2⁶⁴−1 не давал ошибки, сохранялось 2⁶⁴−1.
5. Неудачный `Save` (например, кончилось место) уничтожал прежний файл.
6. При `bad_alloc` во время копирования ключа терялся уже выделенный узел.

Производительность:

1. `istringstream` на каждую строку — около 43% всех инструкций (callgrind).
2. Узел 64 байта (`std::string` + выравнивание), длинные слова — отдельное выделение памяти.
3. `Load` за O(n log n) с поворотами вместо O(n).
4. Лишние вызовы `balance`, когда дерево не менялось.

Утечек и выходов за границы ни `memcheck`, ни `dmalloc`, ни AddressSanitizer не нашли.

## Исправления

- Ключ хранится прямо в узле: `char key[1]` в конце структуры, одно выделение
  `malloc(offsetof(Node, key) + len)`.
- Ручной разбор строки с проверкой формата, на неверную команду — `ERROR: Invalid command`.
- `Save` пишет слова по возрастанию во временный файл и делает `rename`; `Load` проверяет порядок
  и строит сбалансированное дерево из массива за O(n).
- `insert` и `erase` не балансируют дерево, если оно не изменилось.

## Выводы

Перед оптимизацией надо измерять, а не угадывать: больше всего времени ушло не на повороты дерева,
а на `istringstream`. `gprof` видит только код программы, поэтому его стоит дополнять `callgrind`.
`dmalloc` и `memcheck` утечек не нашли, но показали число выделений памяти, и отсюда пришла идея
компактного узла. Самые серьёзные ошибки оказались в разборе ввода и в записи файла, а не в самом
дереве. Итог: в 1.7–2 раза быстрее и на 33–41% меньше памяти.
